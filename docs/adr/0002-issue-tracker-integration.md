# 0002 — Backlog ↔ issue trackers: one table, daemon-owned links

**Status:** accepted (2026-08-12); presentation superseded by
[0004](0004-project-page-surfaces.md) (2026-08-21) — the data decisions below
stand, but the backlog is no longer a paged table, so invariants 11–13 describe
components that no longer exist.

## Context

The project page used to list the *tasks already running* — the same rows the
sidebar shows. That is duplication, not information. What a project page is
missing is the opposite: work that is **not** started yet, from wherever it is
tracked. Teams keep that in GitHub Issues or Linear, and some of it never
belongs in a tracker at all ("try this later").

The obvious reference, Orca, keeps a separate UI per provider (`taskSource ===
'github' ? … : 'linear' ? …`, one 13k-line page component). Its providers never
mix, and adding one means adding another branch of the page.

## Decisions

**One normalized `WorkItem`, one table.** Sources are a *column*, not a
sub-application. The table (`backlog/columns.tsx`) never learns what a provider
is; adapters fill in the same shape. *Rejected:* Orca's per-provider surfaces —
they multiply UI for a distinction the user does not care about, and a project
almost always has exactly one tracker anyway.

**The table is written for this table, not on a generic data-table kit.** Page,
sort and every filter live in one `BacklogParams` object that *is* the React
Query key; `useReactTable` is called once, inline, with `manualPagination /
manualSorting / manualFiltering` and no client row models. *Rejected:* the
diceui/shadcn data-table starter that shipped here first — a `useDataTable`
hook that owned an internal copy of the same state and accepted a controlled
copy alongside it, a meta-driven toolbar that built filter controls from
`columnDef.meta.variant`, and ~3.5k lines of filter-list/filter-menu/date/
slider machinery this board never rendered. The indirection is what hid the
bug: the faceted filter wrote `["done"]` while the view read
`typeof value === "string"`, so Status and Priority silently did nothing. The
board lives in `desktop/src/components/backlog/`, next to the components it is
made of, not in a top-level directory of its own.

**Backlog items are not daemon tasks.** A `Task` is a running agent session; a
work item is something someone wants done. Merging them is what made the old
project page redundant with the sidebar. They are connected by a link, both
ways: `Task.backlog_item_id` and `tracker_links.task_id`.

**The item id is generated by the client, and the daemon keys on it.** The
backlog record's UUID is written first, then the remote issue is created under
it. *Rejected:* keying links on the provider-native id — an item exists before
it reaches a tracker, and it may never reach one.

**The daemon owns credentials and network I/O.** The Linear API key goes
straight from Settings into the OS keychain via the daemon (`security`
CLI, mirroring `claude_auth`); GitHub reuses the `gh` CLI session that PR
creation already needs. *Rejected:* a Linear SDK in the renderer — it would put
a long-lived key in webview-reachable storage.

**Linear talks GraphQL with variables, never string interpolation.** Titles and
bodies are user text; interpolating them into a query string is both a quoting
bug and an injection surface.

**A project reads Linear only through a team it was explicitly pointed at.** The
mapping is daemon state (`tracker_project_settings`), chosen from a live
`tracker.linearTeams` listing in the backlog toolbar. *Rejected:* importing
whatever the key can see, which is what shipped first — a Linear API key is
account-wide, so `adopt_imported` stamped the currently-open project onto the
same issues every time, and five Linear issues appeared in *every* project.
*Also rejected:* putting the mapping in `.warpforge/workspace.yaml` — a team id
belongs to one person's Linear account, not to a checkout that is committed and
shared, and asking someone to hand-write an id when the API can list the teams
is busywork. Changing or clearing the mapping deletes the rows the previous team
imported (`imported = 1` links only; an item written here and pushed out is
local work).

**GitHub status is read-only.** Its useful status lives in project boards, whose
columns are per-project and unmappable to a fixed vocabulary. Warpforge shows
the remote label verbatim and never writes it back. Linear states are mapped
onto the normalized statuses.

*Amended 2026-08-25:* the board column is now **read**, and mapped like a Linear
state. The original decision left every GitHub row saying "To do" forever, which
is not neutral — it is wrong on a board where the same issues read "In Progress"
and "In Test". The read stays read-only: warpforge never writes a column back.
Issues come from GraphQL (`projectItems → fieldValueByName("Status")`, which
needs the `project` token scope) and the column name — not `OPEN`/`CLOSED` — is
what `remoteStatus` shows. A token without the scope, or a repo on no board,
falls back to the `gh issue list` listing and open/closed. Mapping is by
substring (`normalize_status`), because columns are named by whoever built the
board; an unmappable name still lands on `todo` for an open issue, which is
invariant 6 unchanged. A *closed* issue is done (or `cancelled`, for GitHub's
`NOT_PLANNED`) whatever column it sits in.

**Opening a project pulls once; there is no timer.** The board runs one
`import + sync` on mount, gated by a 5-minute staleness window, and the Sync
button is the *same* query refetched — a manual refresh and the automatic one
cannot race. *Rejected:* background polling on an interval (a rate limit is a
bad thing to learn about from a bug report), and mount-with-no-auto-pull (an
empty board with a hidden Sync button hides the one control that would fill it,
which is exactly how this was first shipped and immediately wrong).

**Import and sync are one listing, not two.** `workItem.syncExternal` alone
cannot fill an empty board — it only refreshes items that are *already linked*.
`workItem.importExternal` fetches the tracker's issues once and, in a single
pass over that result, adopts the ones warpforge has never seen (minting the
item id and persisting the link) *and* refreshes the status of the ones it
already tracks. Both are deduplicated on `(provider, external_id)`, so an issue
created from warpforge is never imported back as a second row. Running the two
as separate fetches doubled the daemon's busy time on every project open for no
extra information.

## Invariants

1. **No tracker network call may run inside the actor.** The actor loop is
   single-threaded and awaits its handlers inline (ADR-0001, invariant 9), so a
   `gh` spawn or a Linear request made in there stalls *every* project — chat,
   navigation, services — until the network answers. Tracker RPCs run the
   network on the request task in `server.rs` and go through the actor only for
   store writes. This was shipped wrong once and froze the whole app.
2. **`Store` is not `Send`.** Its rusqlite `Connection` must never be borrowed
   across an `.await`. Hence the three-phase shape: actor hands out rows →
   caller does the network → actor persists. A handler that holds `self.store`
   through an await fails to compile with an error pointing at
   `tokio::spawn(daemon.run(...))`, far from the real cause.
3. **Status reads are per-listing, never per-item.** `github_issue_state` used
   to cost two `gh` spawns per row (resolve `owner/repo`, then read the issue),
   so a twenty-item board meant forty sequential subprocesses. One
   `gh issue list` / one Linear `team.issues` query covers the whole board.
4. **Every tracker call is bounded** (`NETWORK_TIMEOUT`, `kill_on_drop`). It
   runs on the request path, so an unbounded call is a hung UI.
5. **A failed external create rolls the local row back.** The drawer writes the
   local record first (it owns the id), so an error path that leaves it behind
   produces an item claiming to live in a tracker it never reached.
6. **Unknown remote status labels do not overwrite the normalized status.**
   Only the five values warpforge knows are accepted; anything a tracker's own
   vocabulary cannot be mapped onto is kept in `remoteStatus` for display and
   leaves the normalized status alone. `normalize_status` returning `None` is
   that case, and it is why it returns an `Option` rather than defaulting.
7. **`tracker.links` returns an empty list in demo mode, not an error.** The
   desktop's demo transport answers unknown methods with `{}`, so every tracker
   client method must tolerate missing fields.
8. **A provider that is not connected is skipped, not fatal.** `fetch_importable`
   logs and continues, so a GitHub-only project does not fail its import because
   Linear is absent.
9. **No filter or sort control may keep its own copy of the query.** A control
   reads from `BacklogParams` and writes back through `onChange`; anything that
   stores a filter value in a second place will disagree with the request that
   was actually sent, which is exactly how Status and Priority came to be inert
   while looking selected. The one exception is the search box, whose local
   draft is debounced into `params.search`. Since 2026-08-25 that one object
   lives in the UI store keyed by project and is persisted — reading a board as
   "assigned to me" is a stance, not a per-visit keystroke — with the search
   term stripped on the way to storage, because a term typed days ago reopens a
   narrowed list whose reason is invisible.
10. **Status and priority sort by rank, never by their word.** Both storage
    backends order on `status_rank` / `priority_rank` (and their
    `*_RANK_SQL` twins), because alphabetical order puts `high` before `low`
    before `urgent`. Ties break on `id ASC` in both, or paging repeats rows.
11. **`backlogColumns` is a module constant and the row actions ride in
    `table.options.meta`.** TanStack rebuilds its column and cell model when the
    `columns` array's identity changes; building it from callback props meant
    `Projects` re-rendering on every daemon snapshot rebuilt every cell. Never
    close over a prop in a column def.
12. **The pager reports the page the response carried, not the page that was
    requested.** With `keepPreviousData` the grid still shows the old page while
    the next is in flight; a pager reading `params.page` would have moved ahead
    of the rows, which is indistinguishable from "paging back did nothing".
13. **Never animate `opacity` on `<thead>`/`<tbody>`.** In the Tauri WebView
    that promotes the section to its own compositing layer, and a transition
    that starts and cancels within a frame (a cached page coming back) leaves
    the cells laid out but unpainted until a hover forces a repaint. Dim the
    wrapping block instead.
14. **Nothing may import Linear issues into a project with no mapped team.**
    `fetch_importable` takes the team id and skips Linear without one; the same
    id scopes `fetch_links_status`, one listing per team rather than per link.
    An unscoped pull is not a smaller bug than a wrong one — it silently fills
    every project with the same rows.
15. **Only `imported = 1` links may be purged.** A backlog item written here and
    pushed to a tracker carries a link too, and its title, body and priority
    exist nowhere else. Links that predate the column default to 0 and are never
    deleted, even though most of them came from the unscoped-import bug.
16. **An imported row carries the tracker's timestamps, not the sync's.**
    `created_at` is the issue's own creation time and `updated_at` its last
    remote change. Stamping the moment of the fetch made every row's Created
    equal its Updated and re-sorted the board on each refresh. `created_at` is
    written once and thereafter only repaired (`Store::set_backlog_created_at`);
    a caller that does not know the issue's creation time must not be able to
    overwrite it.
17. **`rfc3339_secs` is display-only.** It is hand-rolled to avoid a date
   dependency and does not validate its input; never use it where a wrong
   timestamp would change behaviour rather than row order.

**Warpforge owns the assignee of a local item.** *Added 2026-08-25.* A local
item is created on the signed-in GitHub identity — the same login the assignee
filter offers as "you" — and that is editable on the item. Without it a local
item could never carry an assignee, so the filter everyone actually uses hid
every local item, which reads as the backlog losing them. Tracker-sourced items
keep their remote assignee and no control over it: `adopt_imported` adopts the
tracker's answer on each sync, so an edit here would only survive until the next
refresh. *Rejected:* teaching the filter that "local" implies "mine" — it needs
no identity and fixes existing rows for free, but the YAML backlog is committed
to the repository, where a teammate's item is not yours.

## Consequences

- The local zustand store stays the source of truth for title/priority; no
  tracker round-trips those reliably, and the board must work offline.
- A backlog item mirrored to a tracker is a *copy*, not a view. Edits made in
  GitHub/Linear to anything but status are not pulled back.
- A project with a mapped Linear team creates issues in it; without one, a
  Linear issue created from the drawer still lands in the account's first visible
  team, since choosing Linear as the destination is already explicit.
- Keychain storage is macOS-only today (`/usr/bin/security`); other platforms
  report Linear as unavailable rather than storing the key in the clear.
